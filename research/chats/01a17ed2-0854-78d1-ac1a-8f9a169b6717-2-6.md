**A minimal prototype would be a single-platform app that listens from the bedside, estimates breathing, and updates experimental sleep-stage probabilities every 30 seconds.** I would start with the microphone, one supported phone model, and one adult sleeping alone.

One correction to my earlier answer matters here: the home study reporting 76.2% accuracy used a model that consumes 20 minutes of audio and predicts the middle 10 minutes. It therefore uses future audio relative to its predictions. **That result does not establish real-time accuracy.** A live model needs separate validation using only past and current recordings. [Study methods](https://www.jmir.org/2023/1/e46216)

The smallest useful design would look like this:

| Component | Proposed prototype |
|---|---|
| Setup | Phone plugged in on bedside table; a brief placement check reports whether breathing is detectable |
| Capture | Continuous microphone audio, processed locally |
| Breathing estimator | Estimate rate and breath-to-breath variability over a rolling 60-second window; refresh every 5 seconds |
| Stage estimator | Use audio features and several minutes of preceding context to predict **wake / non-REM / REM**, every 30 seconds |
| Uncertainty | Display “insufficient signal” or “uncertain” when appropriate |
| Recording | Save timestamps, estimates, signal quality, and model version; optional consented audio retention for validation |
| Results | Live display plus an overnight timeline and export |

Those window sizes are **starting design choices**, not validated settings. I would defer light-versus-deep sleep until the broader classification works.

The processing pipeline would be:

```text
Microphone
    ↓
Audio quality checks
    ├─ Breathing detection → rate + variability
    └─ Audio features → model using preceding context
                              ↓
                  Stage probabilities + uncertainty
                              ↓
                     Live display and log
```

**I would not make breathing rate the sole input to staging.** Keep the richer audio features: reducing everything to breaths per minute discards potentially useful information. Conversely, a stage prediction should not imply that individual breaths were successfully measured.

The screen could show:

> Breathing: 14 breaths/min · good signal  
> Experimental estimate: non-REM  
> Updated 8 seconds ago  
> [Start / Stop] [Overnight timeline]

Stage probabilities should only be presented as meaningful confidence percentages after checking their calibration.

The main dependency is **a suitable trained model and paired audio/sleep-study data**. The app shell and breathing pipeline can be built independently, but rules such as “slow breathing means deep sleep” would not make a scientifically credible staging prototype. If suitable model weights and licensing are unavailable, model development becomes a separate research task.

For acceptance, I would require:

- **Engineering:** an eight-hour locked-screen run with logged interruptions, processing latency, battery use, and missing data.
- **Breathing:** comparison with synchronized reference respiration, reporting error **and the proportion of time a usable estimate exists**.
- **Staging:** comparison with independently scored polysomnography on held-out participants, reporting per-stage performance and a confusion matrix.
- **Real-time integrity:** replaying a recording only up to time *t* must produce the same prediction saved live at *t*.

The first practical experiment is simple: **can the chosen phone detect quiet breathing reliably from the intended bedside position?** If that fails, microphone-only staging may still exploit other sounds, but it would not satisfy your breathing-monitoring goal. Speaker-and-microphone sonar would then be a reasonable second sensing approach.
